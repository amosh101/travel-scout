## JOB 1 — Itinerary bug, fix, and proof

### Diagnosis (how the bug was actually traced)

The job brief said "GET /api/itineraries returns 401". That endpoint is the **list-saved** endpoint (`backend/app/routers/itineraries.py:267`), not the one the `/itineraries` page calls. The page calls the **discover** endpoint (`backend/app/routers/itineraries_discover.py:744`). Both are valid probes — the 401 on `GET /api/itineraries` confirms `get_current_user` requires a Bearer token (correct), and the page does not call that endpoint at all.

The actual problem was on `/itineraries` → `/api/itineraries/discover`. The flow is:

1. User has `travel_scout_token` in localStorage (could be a valid JWT, an expired JWT, or garbage — frontend can't tell).
2. Page mounts → `useAuth()` reads the token into React state.
3. `useEffect` fires → `apiFetch('/api/itineraries/discover')` runs with `Authorization: Bearer ***`.
4. Backend's `get_optional_user` (`backend/app/routers/auth.py:160-185`) decodes the JWT. If expired/garbage, it returns `None` silently — *not* a 401.
5. The route handler in `itineraries_discover.py` then treats the request as anonymous, looks up the profile, finds none, and returns **HTTP 400** "anonymous discover requires ?destination=" (`backend/app/routers/itineraries_discover.py:744`+).
6. Frontend's catch block (`frontend/app/itineraries/page.tsx` pre-fix) had branches for 401 and 409 but not 400-with-stale-token — it fell through to `setErr(e.message)`, rendering **"HTTP 400 on /api/itineraries/discover"**, a raw error with no recovery path.

The bug was three-fold:

- **Silent stale-token downgrade** (backend, intentional — but the page wasn't written to expect it)
- **No `?destination=` fallback** for the no-token case (backend, also intentional — anonymous preview needs a destination)
- **No catch-arm for "400 + token present"** (frontend — `page.tsx` pre-fix)
- **No "log in" CTA** when an unauthenticated user lands on `/itineraries` with no destination (frontend)

`commit d1a127e` did not change the load logic; the regression existed in earlier code. The fix is committed as a separate commit so the diff is auditable as "fix(ui): /itineraries stale-token recovery + no-token short-circuit".

### The fix

Two additions to `frontend/app/itineraries/page.tsx`:

1. **Short-circuit guard** at the top of `useEffect` (lines 113-117): if `!token && !urlDestination`, skip the network call and set a friendly message ("Log in to see itineraries built from your profile — or pick a destination to preview"). This avoids the guaranteed 400 that no auth context could ever rescue.
2. **Session-repair path** in the catch block (lines 139-144): if `status === 400 && token` (stale-token downgrade) OR `status === 401`, clear the dead token via `setToken(null)`, set the user-facing message "Your session expired — log in again", and re-render. The next render short-circuits via the guard above — no infinite loop.
3. **Recovery CTAs**: when `err && !token`, the page now renders login + signup buttons so the user has an exit (lines 360-381).
4. **Separate 400-without-token branch** (lines 146-151): "Pick a destination from the home page, or log in to see itineraries built from your profile."

The fix is **minimal, additive, and hot-reloaded** by Next.js. Container logs from `travel-scout_web_1` show `✓ Compiled in 2.2s ... 3.4s ...` confirming the dev server picked up the change.
